AI Campus Pathfinding — BFS, DFS, Greedy & A*

This project implements and compares four classical graph-search algorithms on a real campus map layout. It was built to solidify understanding of uninformed vs. informed search strategies, time/space complexity trade-offs, and algorithm correctness — core pillars of the AI software development process.

View Project Details on GitHub

Software Development Process

The project followed an iterative, test-driven approach. Each algorithm was isolated, implemented, verified manually against the known campus graph, then integrated into a unified runner so results could be compared side-by-side. The campus nodes and edges were modelled first as an abstract adjacency list before any code was written — a deliberate design-before-code discipline.

Algorithm Breakdown

🔵

BFS — Breadth-First Search

Explores all nodes at the current depth before going deeper. Uses a deque as a FIFO queue. Guarantees the shortest path in unweighted graphs. Space complexity: O(V).

🔴

DFS — Depth-First Search

Dives as deep as possible down a branch before backtracking. Uses a stack (LIFO). Memory-efficient but does not guarantee the shortest path. Space complexity: O(depth).

🟡

Greedy Best-First

Always expands the node closest to the goal using a heuristic h(n) — Manhattan distance. Fast but can be misled and does not guarantee optimality.

🟢

A* Search

Combines actual cost g(n) and heuristic estimate h(n): f(n) = g(n) + h(n). Optimal and complete with an admissible heuristic. The gold standard for pathfinding.

Key Design Decisions

All four algorithms share the same campus graph — a hand-crafted adjacency list representing real node relationships (Library → Admin → Lab, etc.). The heuristic function h(n) uses Manhattan distance computed from stored (x, y) coordinates for each node, making it admissible and consistent. The live output via time.sleep() was intentional — it simulates the step-by-step "thought process" of each algorithm, turning a terminal script into an educational tool.

A deliberate architectural choice was to keep each algorithm in its own file (BFS.py, DFS.py, Greedy.py, A_Star.py) rather than a single monolithic script — enforcing the Single Responsibility Principle and making each implementation independently testable.

Secure Image Steganography — PRNG + XOR + LSB

A full-stack Java desktop application that conceals any file inside a PNG image using a three-layer security pipeline: PRNG-shuffled pixel selection, XOR cipher encryption, and Least Significant Bit (LSB) substitution. Designed for point-to-point transmission over an ESP32 wireless link.

View Project Details on GitHub

Software Development Process

The system was engineered top-down — starting with a threat model (what must an attacker not be able to do?), then deriving the cryptographic requirements, then designing the data pipeline, and finally building the Swing GUI as the outermost layer. This security-first SDLC approach ensured that no convenience feature ever compromised the core encoding/decoding contract.

Three-Layer Security Pipeline

1

PRNG Pixel Shuffling

Instead of writing data sequentially into pixels (easily detected by steganalysis), the pixel write-order is randomised using a seeded PRNG (java.util.Random). Without the correct seed, an attacker cannot even locate where bits are hidden. The same seed deterministically recreates the order on decode.

2

XOR Cipher Encryption

Before embedding, the secret file bytes are XOR-encrypted with a keystream produced by a second, independent seeded PRNG (PRNGXORCipher). XOR is self-inverse — the same operation both encrypts and decrypts — making the cipher symmetric and stateless. Payload is unreadable even if extracted correctly.

3

LSB Substitution

Each bit of the encrypted payload replaces the Least Significant Bit of the R, G, and B channel of a selected pixel (3 bits/pixel). This causes a maximum colour shift of ±1 per channel — perceptually invisible and producing PSNR values typically above 50 dB.

Embedded Binary Stream Format

The payload written into the image is self-describing — a decoder needs only the seed to reconstruct everything:

[ 32 bits : encrypted data length (int) ] [ 8 bits : file extension length ] [ n×8 bits : extension chars (ASCII) ] [ m×8 bits : XOR-encrypted file bytes ]

The header is stored unencrypted (but in randomised pixel order) so the decoder can determine how many bytes to extract before decrypting. A sanity check rejects obviously bogus dataLength values (> 50 MB) to guard against wrong seeds producing garbage reads.

Module Architecture

🔐

Encoder.java

Encrypts payload, builds the binary stream, shuffles pixels via PRNG, and writes LSBs into a copy of the carrier image.

🔓

Decoder.java

Replicates the pixel shuffle order, reads LSBs back to binary, parses the header, and decrypts the payload with a fresh PRNGXORCipher.

🔑

PRNGXORCipher.java

Stateless symmetric cipher. Each call creates a freshly seeded PRNG — encrypt and decrypt are therefore independent and ordering-free.

🖥️

MainFrame.java

Tabbed Swing window hosting Encode, Decode, and Transmit (ESP32) panels. Uses system Look & Feel for native OS appearance.

📤

EncodePanel.java

Carrier image browser, PRNG seed field, secret file picker, capacity checker, and post-encode MSE/PSNR metric display.

📥

DecodePanel.java

Stego image loader (from disk or pushed from the Transmit tab), seed input, live decode log, and file save dialog.
